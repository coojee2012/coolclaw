# CoolClaw AI Agent 增强开发计划 — 2025.08.22

## DDD (Domain-Driven Design) 驱动的架构演进

> 目标: 将 CoolClaw 从"有工具的 LLM"升级为"真正的自主 AI Agent"
> 方法论: Domain-Driven Design — 以领域模型为核心组织代码和行为

---

## 一、DDD 核心概念在 CoolClaw 中的映射

### 1. 领域 (Domain)

**代码开发** — 这是 CoolClaw 的核心业务领域。

### 2. 子域 (Subdomains)

```
代码开发领域
├── 核心域 (Core Domain): 代码理解与修改
│   ├── 代码分析 (Analysis)
│   ├── 代码生成 (Generation)
│   └── 代码验证 (Verification)
│
├── 支撑域 (Supporting Domain): 开发流程
│   ├── 版本管理 (Version Control)
│   ├── 测试执行 (Test Execution)
│   └── 文档查询 (Documentation)
│
└── 通用域 (Generic Domain): 基础设施
    ├── 文件系统 (File System)
    ├── 网络访问 (Network)
    └── 命令执行 (Command Execution)
```

### 3. 限界上下文 (Bounded Contexts)

```
+----------------------------------------------------------+
|                    Orchestrator Context                    |
|                  (任务规划与协调)                           |
+----------------------------------------------------------+
         |                    |                    |
         v                    v                    v
+------------------+ +------------------+ +------------------+
| Analysis Context | | Implementation   | | Verification     |
| (代码理解)       | | Context          | | Context          |
|                  | | (代码实现)       | | (代码验证)       |
| Tools:           | | Tools:           | | Tools:           |
| - codegraph_*    | | - write_file     | | - lsp_diagnostics|
| - read_file      | | - edit_file      | | - run_test       |
| - lsp_goto_def   | | - run_command    | | - git_diff       |
| - lsp_find_ref   | |                  | | - git_blame      |
+------------------+ +------------------+ +------------------+
         |                    |                    |
         +--------------------+--------------------+
                              |
+----------------------------------------------------------+
|                   Infrastructure Context                  |
|              (文件系统 / 网络 / Git / LSP)                |
+----------------------------------------------------------+
```

### 4. 通用语言 (Ubiquitous Language)

| 领域概念 | 代码表达 | 说明 |
|----------|----------|------|
| 工具调用 | `ToolCall(name, args)` | Agent 执行一个原子操作 |
| 工具结果 | `ToolResult(name, content, success)` | 工具执行的返回 |
| 任务规划 | `_plan_task(user_request)` | 拆解为编号步骤 |
| 工作区 | `workdir: Path` | Agent 操作的安全边界 |
| 领域事件 | `DomainEvent(type, payload)` | 工具调用产生的事件 |
| 上下文注入 | `inject_context(memory)` | 记忆注入系统提示 |

### 5. 聚合 (Aggregates)

```
聚合 1: 代码修改 (Code Modification Aggregate)
├── 聚合根: EditOperation
├── 实体: read_file -> edit_file -> lsp_diagnostics
├── 一致性边界: 单次编辑操作的原子性
└── 领域事件: CodeModified, DiagnosisCompleted

聚合 2: 提交变更 (Commit Aggregate)
├── 聚合根: CommitOperation
├── 实体: git_status -> git_diff -> git_commit
├── 一致性边界: 暂存+提交的原子性
└── 领域事件: ChangesCommitted, BranchSwitched

聚合 3: 代码分析 (Analysis Aggregate)
├── 聚合根: AnalysisOperation
├── 实体: codegraph_search -> read_file -> lsp_diagnostics
├── 一致性边界: 一次完整分析的原子性
└── 领域事件: CodeAnalyzed, SymbolsFound
```

### 6. 领域事件 (Domain Events)

```python
@dataclass
class DomainEvent:
    type: str           # ToolCallStarted, ToolCallCompleted, TaskPlanned...
    agent_id: str       # 哪个 Agent 触发
    tool_name: str      # 工具名
    args: dict          # 工具参数
    result: Any         # 工具结果
    timestamp: float    # 时间戳
    context: str        # 所属限界上下文
```

事件流:
```
UserRequest
  -> TaskPlanned(steps=[...])
  -> ToolCallStarted(codegraph_search)
  -> ToolCallCompleted(codegraph_search, symbols=[...])
  -> ToolCallStarted(read_file)
  -> ToolCallCompleted(read_file, content=...)
  -> ToolCallStarted(edit_file)
  -> ToolCallCompleted(edit_file, success=True)
  -> SelfReviewStarted(lsp_diagnostics)
  -> SelfReviewCompleted(errors=0)
  -> CodeModified(file=src/agent.py)
  -> ChangesCommitted(commit=abc123)
```

### 7. 防腐层 (Anti-Corruption Layer)

```
MCP Server = Anti-Corruption Layer
├── 翻译层: LLM 的 TOOL:xxx() 格式 <-> MCP 工具调用
├── 安全层: 路径校验、命令拦截
├── 协议层: MCP JSON-RPC <-> Python 函数调用
└── 适配层: 不同工具的参数校验和错误处理
```

## 二、现状评估

### 已有能力 (27 MCP 工具)

| 限界上下文 | 工具 | 数量 |
|------------|------|------|
| 基础设施 | list_files, read_file, write_file, edit_file, run_command | 5 |
| 代码分析 | codegraph_search, codegraph_explore, codegraph_list_symbols | 3 |
| 代码验证 | lsp_diagnostics, lsp_goto_definition, lsp_find_references, lsp_rename, lsp_document_symbols | 5 |
| 版本管理 | git_status, git_log, git_diff, git_diff_staged, git_blame, git_branch, git_commit, git_checkout | 8 |
| 网络 | web_search, fetch_url | 2 |
| 测试 | run_test | 1 |
| 文档 | resolve_library_id, query_docs | 2 |

### 已实现的 Agent 能力

- 任务规划 (_plan_task): 复杂任务拆解为编号步骤
- 并行工具执行 (asyncio.gather): 只读并行，写入串行
- 自我审查: write/edit 后自动 lsp_diagnostics
- 上下文管理: 自动裁剪早期工具结果
- 跨会话记忆 (ProjectMemory): 文件持久化

### 核心瓶颈 (DDD 视角)

1. **限界上下文边界模糊**: Agent 可以随意调用任何工具，没有上下文约束
2. **缺少领域事件**: 工具调用没有事件驱动，无法追踪和学习
3. **防腐层不完整**: 沙箱缺失，安全边界不存在
4. **记忆未注入上下文**: 项目记忆存在但未被领域模型消费

## 三、DDD 驱动的开发计划

### Phase A: 基础设施层 (Infrastructure Context)

#### A1. 工作区沙箱 (防腐层 - 安全边界)

**目标**: 在防腐层建立路径校验和命令拦截

**DDD 概念**: Anti-Corruption Layer (防腐层)

```
实现层级:
  Level 1 (立即): 路径白名单校验
    - 所有文件操作工具增加 workdir 校验
    - 离开 workdir 的操作被拒绝
    - 成本: 低, 1-2 天

  Level 2 (短期): 命令黑名单
    - run_command 拦截 rm -rf /, chmod 777, sudo 等
    - 沙箱模式下只允许 git/python/pip/npm 等安全命令
    - 成本: 低, 1 天

  Level 3 (中期): Docker 沙箱 (可选)
    - run_command 在 Docker 容器内执行
    - 挂载 workdir 为 volume
    - 成本: 中, 3-5 天
```

**文件变更**:
- `src/mcp/combined.py`: 所有文件工具增加 `_validate_path(path, workdir)` 校验
- `src/mcp/combined.py`: run_command 增加命令白名单/黑名单
- `src/agent.py`: Agent 初始化时传入 workdir，传递给 MCP Server
- `config.yaml`: 新增 `sandbox.enabled`, `sandbox.allowed_commands` 配置

**验收标准**:
- [ ] read_file("../../../etc/passwd") 返回 "access denied"
- [ ] run_command("rm -rf /") 被拦截
- [ ] run_command("git status") 正常执行
- [ ] 工作区内所有文件操作正常

---

#### A2. 真实流式输出 (领域事件 - 实时通知)

**目标**: 工具调用产生领域事件，实时推送到前端

**DDD 概念**: Domain Events (领域事件)

```
实现步骤:
  1. local_llm.py: LLM.generate() 改为 yield token 模式
     - llama-cpp-python 原生支持 callback 生产者
     - 每个 token 生成时 yield 出来

  2. agent.py: Agent.run() 增加 stream=True 参数
     - 工具调用之间 yield "思考中..." 消息
     - 工具执行时 yield "正在执行 git_status..." 消息
     - 最终回复 yield 真实 token

  3. api.py: /api/chat/stream 使用真正的 async generator
     - 移除 _fake_stream
     - 直接 yield agent 的 streaming 输出

  4. gemini_client.py: Gemini API 原生 streaming
     - Google AI SDK 已支持 stream=True
```

**文件变更**:
- `src/local_llm.py`: generate() 增加 `stream=True` 参数，返回 AsyncGenerator
- `src/agent.py`: run() 增加 stream 参数，yield 中间状态
- `src/api.py`: /api/chat/stream 重写为真实 streaming
- `src/gemini_client.py`: 适配 streaming 接口

**验收标准**:
- [ ] curl SSE 端点可看到逐 token 输出
- [ ] 工具调用期间有实时状态消息
- [ ] 前端聊天界面实时显示

#### A3. 持久化记忆消费 (限界上下文 - Orchestrator)

**目标**: Agent 启动时加载历史记忆，注入 Orchestrator 上下文

**DDD 概念**: Context Injection (上下文注入)

```
实现步骤:
  1. agent.py: Agent.__init__ 加载 ProjectMemory
     - 获取最近 10 条决策记录
     - 获取最近 5 条错误学习
     - 生成 "项目经验摘要" 注入 system prompt

  2. dispatcher.py: 系统提示增加记忆段落
     - "[项目经验] 以下是本项目的历史决策和教训:"
     - Agent 可以参考历史避免重复错误

  3. Agent 完成任务后自动记录
     - 每次 run() 结束后调用 save_summary()
     - 遇到 edit_file 错误时调用 record_error()
```

**文件变更**:
- `src/agent.py`: __init__ 加载 ProjectMemory，注入上下文
- `src/agent.py`: run() 结束后自动 save_summary()
- `src/agent.py`: edit_file 失败时自动 record_error()
- `src/dispatcher.py`: 系统提示增加记忆段落模板

**验收标准**:
- [ ] Agent 重启后能引用上次的决策
- [ ] 第二次犯同样错误时 Agent 主动避免
- [ ] .coolclaw_memory/ 目录有持续增长的记录

### Phase B: 核心域 (Core Domain)

#### B1. Function Calling Schema (防腐层 - 结构化调用)

**目标**: 将 prompt-based 工具调用升级为结构化 JSON schema

**DDD 概念**: Anti-Corruption Layer (防腐层 - 协议适配)

```
实现步骤:
  1. 定义 Tool Schema 注册表
     - 每个 MCP 工具生成 OpenAI function calling 格式的 JSON schema
     - 27 个工具 = 27 个 schema 定义

  2. LLM 接口抽象
     - local_llm.py: 支持 tools 参数 (llama.cpp function calling)
     - gemini_client.py: 支持 tools 参数 (Google FC)
     - 返回结构化的 tool_calls 而非文本

  3. Agent 循环适配
     - 解析结构化 tool_calls (非文本解析)
     - 准确率从 ~70% 提升到 ~95%

  4. 保留 prompt fallback
     - 不支持 FC 的模型退回 TOOL:xxx() 格式
```

**文件变更**:
- `src/mcp/tool_schema.py`: 新文件，27 个工具的 JSON schema
- `src/local_llm.py`: generate() 支持 tools 参数
- `src/gemini_client.py`: generate() 支持 tools 参数
- `src/agent.py`: 优先解析结构化 tool_calls，fallback 到文本解析

**验收标准**:
- [ ] 使用支持 FC 的模型时，工具调用准确率 >90%
- [ ] 不支持 FC 的模型正常 fallback
- [ ] 27 个工具 schema 全部正确

#### B2. 多模型协作 (限界上下文 - 多 Agent)

**目标**: Orchestrator + 多个专业 Agent 协作

**DDD 概念**: Bounded Contexts (限界上下文) + Context Map (上下文映射)

```
限界上下文设计:
  Analysis Context (代码理解):
    - 只有 read_file, codegraph_search, lsp_diagnostics
    - 职责: 理解代码架构，设计方案
    - 模型: 7B (需要理解力)

  Implementation Context (代码实现):
    - 所有文件和编辑工具
    - 职责: 实现代码修改
    - 模型: 7B-Coder (需要编码力)

  Verification Context (代码验证):
    - 只有 read_file, lsp_diagnostics, git_diff
    - 职责: 审查代码质量
    - 模型: 7B (需要判断力)

  Orchestrator Context (协调):
    - 管理上述 Agent 的调度
    - 分配任务，汇总结果
```

**文件变更**:
- `src/agent.py`: Agent 支持 role 参数 (architect/coder/reviewer)
- `src/agent.py`: 新增 Orchestrator 协调逻辑
- `src/dispatcher.py`: 根据任务复杂度选择单 Agent 或多 Agent

**验收标准**:
- [ ] 复杂任务自动拆分为多 Agent 流水线
- [ ] Architect 方案 -> Coder 实现 -> Reviewer 审查
- [ ] 单 Agent 简单任务仍然高效

### Phase C: 高级能力 (1-2 月)

#### C1. WebSocket 实时通信 (领域事件 - 双向流)

**DDD 概念**: Domain Events (领域事件 - 双向推送)

```
实现:
  - FastAPI WebSocket 端点: ws://localhost:8484/ws/chat
  - 双向通信: 客户端发送消息，服务端推送:
    - LLM token 流
    - 工具调用状态 ("正在搜索...")
    - 错误通知
  - 前端 Alpine.js 适配 WebSocket
```

#### C2. 自我反思与回滚 (聚合 - 原子性保证)

**DDD 概念**: Aggregate (聚合 - 事务边界)

```
实现:
  - Agent 检测到 edit_file 后 lsp_diagnostics 报错 > 阈值
  - 自动 git stash 回滚
  - 换策略重试 (最多 3 次)
  - 3 次失败后请求用户介入
```

#### C3. 代码库自动克隆理解 (领域服务)

**DDD 概念**: Domain Service (领域服务)

```
实现:
  - 新工具: clone_and_index(github_url)
  - 自动 git clone -> codegraph init -> 架构摘要
  - 返回: 项目结构 + 技术栈 + 关键文件
  - Agent 可直接开始工作
```

#### C4. 用户偏好学习 (上下文注入)

**DDD 概念**: Context Injection (上下文注入 - 风格适配)

```
实现:
  - .coolclaw_memory/preferences.json
  - 从历史代码变更中学习:
    - 缩进风格 (2/4 spaces)
    - 命名规范 (snake_case/camelCase)
    - 注释偏好
  - 注入 Agent 上下文，输出风格与用户一致
```
